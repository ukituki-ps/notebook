# Feature brief — f-v5-sverka (черновик, s01)

Черновик брифа по трём постановкам. Не спека, не план, не архитектура и не
декомпозиция: границы объёма и проверяемые правила фиксирует product, решение
о структуре — architect, нарезка на юниты — planner.

## 1. Проблема

Сотрудники ГК сверяют списки застрахованных, присланные СК, с данными системы
вручную. Ручная сверка не даёт единого воспроизводимого снимка результата,
теряет историю прошлых сверок и не формирует готовый запрос в СК по
расхождениям. Из-за этого расхождения обрабатываются долго, а результат
невозможно перепроверить «как было на момент сверки».

## 2. Цель

Дать сотруднику ГК один раздел «Сверка застрахованных», в котором можно:

1. загрузить список ЗХ от СК в едином шаблоне и получить проверку файла до
   запуска;
2. получить категоризированный результат сверки только по ЗХ «Прикреплен» с
   точным сравнением и сохранённым снимком результата;
3. выгрузить результат в Excel, включая готовый лист «Запрос в СК»;
4. вернуться к прошлым сверкам: открыть результат, скачать исходный файл,
   повторить сверку по текущим данным;
5. увидеть по строке расхождения договоры и заявки ЗХ со ссылками на карточки.

## 3. Пользователи и роли

| Роль | Доступ | Что делает |
|---|---|---|
| Сотрудник ГК (пользователь) | Полный доступ к разделу | Выбирает ГК и СК, скачивает шаблон, загружает файл, запускает сверку, смотрит/фильтрует результат, выгружает Excel, открывает историю и карточки договоров/заявок |
| Пользователь клиента (HR) | **Раздел недоступен** | Не видит раздел «Сверка застрахованных»; прямой URL и серверные операции раздела не должны давать доступ к данным сверок |

В шапке результата и в истории отображается «кто запустил» — ФИО
пользователя, запустившего сверку. Пользователям клиентов (HR) раздел
недоступен.

В постановках нет других ролей. Как система отличает пользователя клиента
(HR) и какие ещё роли видят раздел — открытый вопрос OQ-11; расширение ролевой
модели за пределы запрета HR в объём не входит.

Согласно постановке «История сверок» пользователь видит сверки **всех**
пользователей, а не только свои (это позволяет коллеге продолжить работу).
Подтверждение этого решения — OQ-05.

## 4. Объём: три постановки

Границы объёма коротко: **внутри** — раздел сверки, проверка и сопоставление
файла, снимок результата, Excel с тремя листами, история сверок, live-колонки
договоров/заявок в результате и выгрузке. **Вне** — нечёткий поиск, изменение
данных ЗХ, отметки «обработано»/комментарии, ответ СК и отправка запроса,
удаление и сравнение сверок, создание/наполнение справочников ГК/СК/ЗХ и
данных договоров/заявок, роли сверх запрета HR. Детализация — `do[]`,
`dont[]`, `out_of_scope[]` (§6–§8).

### 4.1 Базовая постановка «Сверка застрахованных с данными СК» (v2) — предпосылка

Базовая постановка самодостаточна: раздел, загрузка файла, проверки,
сопоставление, экран результата, выгрузка в Excel. Оба дополнения опираются на
неё и не могут быть реализованы раньше неё.

| Требование | Продуктовый результат (полный объём) |
|---|---|
| FR-01. Загрузка файла и запуск сверки | Раздел «Сверка застрахованных»; выбор ГК и СК (СК — только те, у кого есть договоры с ЮЛ выбранной ГК; поле неактивно до выбора ГК, сбрасывается при смене ГК); «Скачать шаблон» всегда активна и отдаёт «Шаблон сверки застрахованных.xlsx»; загрузка одного .xlsx перетаскиванием или выбором (новый файл заменяет предыдущий); «Запустить сверку» активна только при ГК+СК+файл; проверки E1–E7; колонки ищутся по названию (порядок колонок и лишние колонки ошибкой не являются); все ошибки сразу в таблице «Строка / Колонка / Ошибка»; пустые строки пропускаются; после ошибки ГК, СК и файл сохраняются; раздел недоступен HR |
| FR-02. Сопоставление и категории | Сверяются только ЗХ «Прикреплен»; сравнение ФИО/программы/договора точное, не учитываются только регистр и лишние пробелы; договор — любой договор ЗХ, включая прошлые; 13 категорий: Совпало; Есть в СК, нет в системе; Есть в системе, нет в СК; Другое ЮЛ; Расхождение в ФИО; Расхождение в дате рождения; Расхождение по программе («Отличие только в знаках» / «Другая программа»); Доп. программа в СК; Дубль в списке СК; Задвоение у СК; Дубль в системе; справочные — В процессе у нас, Переход между ЮЛ; особые случаи: несколько подходящих ЗХ → строка «Есть в СК, нет в системе» + «Найдено несколько ЗХ», а ЗХ → «Дубль в системе»; основная+доп. программа одного ЗХ — не дубль; отличие в 2+ частях ФИО — пара не ищется (строка → «Есть в СК, нет в системе», ЗХ → «Есть в системе, нет в СК»); ЗХ «в процессе» без строки в файле — только в свод; результат сохраняется на момент сверки и не пересчитывается; статусы «Обрабатывается», «Готова», «Ошибка обработки» |
| FR-03. Экран результата | Шапка (ГК, СК, дата/время, кто запустил, статус, ссылка на исходный файл, «Выгрузить в Excel»); W1 (договоры ГК↔СК, которых нет в файле) и W2 (численность отличается в 2 раза и более в любую сторону); свод по договорам с итоговой строкой и фильтрацией кликом по числу; список расхождений с колонками категория/договор/ЮЛ/ФИО СК/ФИО система/ДР СК/ДР система/программа СК/программа система/№ полиса/статус ЗХ/комментарий; подсветка отличающихся значений; фильтры (категория — несколько, договор, поиск по ФИО, «Показывать для справки» включён); сортировка по порядку категорий, затем по ФИО; I1 «Сверка выполняется…» до готовности с автообновлением без перезагрузки; I2 «Расхождений не найдено» |
| FR-04. Выгрузка в Excel | Кнопка активна только для «Готова», иначе E8 «Выгрузка доступна после завершения сверки»; файл «Сверка <ГК> <СК> <ДД.ММ.ГГГГ>.xlsx» (дата запуска), весь результат независимо от фильтров; листы «Свод по договорам» (+ дата, ГК, СК, правила сверки), «Расхождения» (то же, что на экране, с подсветкой), «Запрос в СК» (только категории с текстом запроса, колонка «Ответ СК» пустая, без «Дубль в системе», «В процессе у нас», «Переход между ЮЛ»); Arial, шапка с заливкой, фильтры, закреплённая шапка; таблица «Что запросить у СК» — как в постановке |

Явно **не входит** в базовую часть (по постановке): нечёткий поиск, изменение
данных ЗХ, ссылки на договоры/заявки ЗХ, отметки «обработано» и комментарии
пользователя, загрузка ответа СК, отправка запроса из системы.

### 4.2 Дополнение «История сверок» (v1)

Дополняет базовую постановку и опирается на то, что базовая уже сохраняет
сверку (файл, статус, результат).

| Требование | Продуктовый результат |
|---|---|
| FR-01. Список сверок | В разделе под формой запуска — список сверок всех пользователей, новые сверху; колонки: дата/время, ГК, СК, кто запустил, статус, «Расхождений» («Итого расхождений»; для не-«Готова» — «—»), исходный файл (скачивание), действия; клик по строке открывает результат; «Повторить» запускает новую сверку с теми же ГК/СК/файлом по текущим данным, прежняя не меняется; фильтры ГК/СК/статус; сортировка по дате; в список попадают только запущенные сверки; I1 «Сверок пока нет» |

Не входит: удаление сверок, сравнение двух сверок между собой.

### 4.3 Дополнение «Договоры и заявки ЗХ в результате сверки» (v1)

Дополняет базовую постановку и требует, чтобы экран результата и выгрузка уже
были реализованы.

| Требование | Продуктовый результат |
|---|---|
| FR-01. Экран результата | В списке расхождений — колонки «Договоры ЗХ» (все договоры ЗХ с ЮЛ, включая прошлые; номер — ссылка на карточку в новой вкладке), «Заявки ЗХ» (все заявки по ЗХ в рамках этих договоров: номер, тип «прикрепление/открепление/изменение», статус, дата; 3 последние в строке, остальные по «еще N»; номер — ссылка), «Действия с нашей стороны» («Есть заявки» / I1 «Действий с нашей стороны не найдено»); данные — на момент открытия экрана, а не сверки; для строк «Есть в СК, нет в системе» — поиск ЗХ ГК с теми же ФИО и ДР в любых статусах и с любыми СК; если найден — показываются его договоры и заявки; ссылки открываются в новой вкладке |
| FR-02. Выгрузка Excel | Те же три колонки на листе «Расхождения», гиперссылки на карточки, все заявки (без лимита 3) через перенос строки; данные совпадают с экраном на момент выгрузки; на листе «Запрос в СК» этих колонок нет |

Не входит: создание заявок с экрана результата.

### 4.4 Отношения и порядок реализации

1. **Базовая постановка v2 — предпосылка для обоих дополнений.** Дополнение
   «История сверок» требует сохранённых сверок и исходных файлов; дополнение
   «Договоры и заявки ЗХ» требует готового экрана результата и выгрузки.
2. Предлагаемый порядок поставки: **база v2 → «История сверок» → «Договоры и
   заявки ЗХ»**. История идёт раньше, потому что зависит только от сохранения
   сверки; договоры/заявки дополнительно требуют данных заявок и адресов
   карточек (OQ-02, OQ-10).
3. Дополнения между собой независимы; порядок между ними — рекомендация
   product, а не декомпозиция. Нарезка на юниты и порядок работ — planner.
4. Объём каждой поставки фиксируется отдельно; смешивать базовую часть с
   колонками договоров/заявок нельзя (см. `dont[]`).

## 5. Текущее состояние продукта: зависимость и риск объёма

Репозиторий notebook — минимальное приложение: Go-сервис с in-memory
хранилищем, аутентификацией (register/login/session), заметками (list/create/
delete) и поиском по заметкам, плюс статический web-клиент. Домена сверки в
коде нет:

- нет сущностей ГК, СК, ЗХ, договоров ЮЛ↔СК, договоров ЗХ, заявок ЗХ и их
  статусов;
- нет источников/интеграций, откуда эти данные берутся, и тестовых данных для
  стенда;
- нет разбора и валидации .xlsx, формирования Excel с тремя листами,
  гиперссылками и форматированием;
- нет хранения файлов и жизненного цикла сверок (текущее хранилище заметок —
  in-memory);
- нет ролевой модели «сотрудник ГК / пользователь клиента (HR)».

Следствие: фича не является малым расширением существующего поведения. Это
новый домен внутри продукта; его объём и оценка зависят от наличия данных,
интеграций, хранения, обработки файлов и ролей. Бриф фиксирует эту зависимость
как риск (R1–R3) и **не проектирует** архитектуру: источники данных, хранение,
фоновую обработку и способ выгрузки определяет architect.

## 9. change_class

**`arch`.**

Обоснование:

- Фича вводит новый домен/подсистему: собственные сущности сверки и строк
  результата, снимок результата, исходный файл, история, ролевой раздел,
  разбор .xlsx и формирование Excel. Это меняет границу системы, а не
  расширяет существующее поведение.
- Фича потребляет данные (ГК, СК, ЗХ, договоры, заявки), которых в репозитории
  нет; понадобятся решения об источниках, хранении и обработке — это
  архитектурные решения.
- Не `plain`: это не локальное расширение существующего API/UI; объём включает
  новое хранилище, фоновую обработку, файлы и выгрузку.
- Не `security`: механизм аутентификации/сессий не меняется; запрет HR —
  одно из требований нового домена (INV-09), хотя оно security-критично и
  подлежит отдельной проверке.
- Не `invariant`: существующие инварианты не меняются; фича вводит **новые**
  инварианты сверки в новом домене (INV-01…INV-11).

## 10. invariants[]

Все инварианты на s01 — `proposed`: реализация и исполнимые оракулы ещё не
существуют. `test_ref` указывает планируемый оракул (unit/contract-тест или
E2E-сценарий). При финализации брифа (s06) активный инвариант обязан получить
исполнимый `test_ref`, иначе он не активируется.

## 11. scenarios[]

Сценарии — наблюдаемые пользователем, исполнимые на стенде и опровержимые
(ADR-KIT-091). Машинный компаньон — `scenarios.json` (schema
`orc.scenarios/v1`); приёмка требует по каждому сценарию пройденный E2E и
непустой скриншот (gate-scenario-coverage).

### SVERKA-E2E-01. Шаблон и ошибки формата/колонок/пустого файла
- **Given** сотрудник ГК в разделе «Сверка застрахованных», выбраны ГК и СК.
- **When** скачивает шаблон; затем загружает .csv; затем .xlsx без обязательной
  колонки «Дата рождения»; затем .xlsx только с заголовками.
- **Then** скачанный файл — «Шаблон сверки застрахованных.xlsx» с колонками
  № договора\\*, ФИО\\*, Дата рождения\\*, Программа\\*, Тип программы,
  Страхователь, № полиса СК, Дата начала программы; .csv → E1 «Загрузите файл
  в формате .xlsx»; без колонки → E3 с названием колонки; без строк → E4 «В
  файле нет данных для сверки»; сверка не запускается.

### SVERKA-E2E-02. Границы дат
- **Given** выбраны ГК и СК, в файле даты 29.02.2024, 29.02.2025, 31.02.2026,
  2026-01-01.
- **When** нажимает «Запустить сверку».
- **Then** 29.02.2024 принимается; 29.02.2025, 31.02.2026 и 2026-01-01 дают E6
  «Некорректная дата. Формат — ДД.ММ.ГГГГ» с номерами строк; сверка не
  запускается.

### SVERKA-E2E-03. Несколько ошибок файла сразу
- **Given** выбраны ГК и СК; в файле в строке 5 пустая дата рождения, в строке 8
  договор не из договоров ГК↔СК, между ними пустые строки.
- **When** нажимает «Запустить сверку».
- **Then** сверка не запускается; таблица «Строка / Колонка / Ошибка» показывает
  обе ошибки сразу с номерами строк 5 и 8 (E5 и E7); пустые строки в ошибках
  отсутствуют; ГК, СК и файл остались выбранными.

### SVERKA-E2E-04. Успешная сверка и экран результата
- **Given** валидный файл с совпадающей парой, откреплённым ЗХ и ЗХ
  «Прикреплен», которого нет в файле.
- **When** запускает сверку.
- **Then** сначала I1 «Сверка выполняется…», затем без перезагрузки статус
  «Готова»; в шапке ГК, СК, дата/время, кто запустил, статус и ссылка на
  исходный файл; свод по договорам с итоговой строкой; список расхождений с
  категориями по правилам; у строки с откреплённым ЗХ комментарий «В системе
  откреплен»; ЗХ «Прикреплен» без строки — «Есть в системе, нет в СК».

### SVERKA-E2E-05. Точное сравнение, категории и дубли
- **Given** в файле кейсы: «ИВАНОВ  ИВАН ИВАНОВИЧ» против «Иванов Иван
  Иванович»; «Петров Пётр Петрович» против «Петров Петр Петрович»; программа
  «Москва.» против «Москва..»; «Москва_new» против «Москва»; пара в договоре
  другого ЮЛ; две одинаковые строки; два ЗХ «Прикреплен» с одинаковыми ФИО и
  ДР; один ЗХ с основной и дополнительной программой.
- **When** запускает сверку и открывает результат.
- **Then** «Совпало» (регистр/пробелы), «Расхождение в ФИО» с частью ФИО и оба
  значения, «Расхождение по программе» с «Отличие только в знаках», «Другая
  программа», «Другое ЮЛ» с обоими номерами договоров, вторая одинаковая
  строка — «Дубль в списке СК», два ЗХ — «Дубль в системе»; строки одного ЗХ
  по основной и дополнительной программе дублем не считаются.

### SVERKA-E2E-06. Фильтры, подсветка, сортировка и справочные категории
- **Given** готовая сверка с несколькими категориями, включая «В процессе у
  нас» и «Переход между ЮЛ».
- **When** кликает число в своде; выбирает несколько категорий; фильтрует по
  договору и ФИО; выключает «Показывать для справки».
- **Then** список фильтруется по договору и категории; подсвечены только
  отличающиеся парные ячейки (например, «ФИО (СК)» и «ФИО (система)»);
  сортировка — по порядку категорий, затем по ФИО; справочные строки скрыты;
  «Итого расхождений» не меняется.

### SVERKA-E2E-07. Пустой результат
- **Given** файл полностью совпадает с ЗХ «Прикреплен», лишних строк и ЗХ нет.
- **When** сверка готова.
- **Then** вместо списка — I2 «Расхождений не найдено»; свод и итоговая строка
  корректны; выгрузка доступна.

### SVERKA-E2E-08. Предупреждения W1 и W2
- **Given** у ГК есть договор с СК, которого нет в файле; по другому договору в
  файле 200 строк, а ЗХ «Прикреплен» в системе 50.
- **When** открывает результат.
- **Then** над сводом W1 с номером отсутствующего договора и W2 с N/M; оба
  предупреждения не блокируют просмотр и выгрузку.

### SVERKA-E2E-09. Выгрузка Excel: три листа и содержимое
- **Given** готовая сверка, на экране включён фильтр по одной категории.
- **When** нажимает «Выгрузить в Excel».
- **Then** скачивается «Сверка <ГК> <СК> <ДД.ММ.ГГГГ>.xlsx» с листами «Свод по
  договорам», «Расхождения», «Запрос в СК»; в файле все строки результата
  независимо от фильтра; итоги свода совпадают с экраном; Arial, шапка с
  заливкой, фильтры, закреплённая шапка; на «Запрос в СК» нет «Дубль в
  системе», «В процессе у нас», «Переход между ЮЛ», колонка «Ответ СК»
  пустая, «Что запросить у СК» соответствует таблице постановки.

### SVERKA-E2E-10. Выгрузка недоступна до готовности
- **Given** сверка в статусе «Обрабатывается» (или «Ошибка обработки»).
- **When** пользователь смотрит на кнопку «Выгрузить в Excel» и пытается
  выгрузить.
- **Then** кнопка неактивна, файл не скачивается; для незавершённой сверки
  показывается E8 «Выгрузка доступна после завершения сверки»; после перехода
  в «Готова» кнопка активна.

### SVERKA-E2E-11. История: открыть, скачать, повторить
- **Given** есть сверки разных пользователей в статусах «Готова»,
  «Обрабатывается», «Ошибка обработки»; одна загрузка не прошла проверку.
- **When** открывает раздел «Сверка застрахованных».
- **Then** под формой список сверок всех пользователей, новые сверху, колонки
  дата/время, ГК, СК, кто запустил, статус, «Расхождений», исходный файл,
  действия; для не-«Готова» «—»; клик по «Готова» открывает результат,
  идентичный сохранённому; исходный файл скачивается; «Повторить» создаёт
  новую сверку с теми же ГК/СК/файлом по текущим данным, прежняя не меняется;
  фильтры ГК/СК/статус работают; сверка из непрошедшего файла в списке
  отсутствует.

### SVERKA-E2E-12. История: пустое состояние
- **Given** в системе нет запущенных сверок.
- **When** открывает раздел.
- **Then** вместо списка I1 «Сверок пока нет»; форма запуска доступна.

### SVERKA-E2E-13. Дополнение: колонки, ссылки, 3 заявки + «еще N»
- **Given** готовая сверка, у ЗХ два договора и пять заявок; у другого ЗХ заявок
  нет.
- **When** открывает результат (дополнение реализовано).
- **Then** в списке есть «Договоры ЗХ», «Заявки ЗХ», «Действия с нашей стороны»;
  номера договоров и заявок — ссылки, открываются в новой вкладке; в строке
  видны 3 последние заявки (номер, тип, статус, дата), остальные — по «еще N»;
  у ЗХ с заявками «Есть заявки»; у ЗХ без заявок — I1 «Действий с нашей
  стороны не найдено».

### SVERKA-E2E-14. Дополнение: «Есть в СК, нет в системе» и данные на момент открытия
- **Given** в ГК есть откреплённый ЗХ с теми же ФИО и ДР, что у строки «Есть в
  СК, нет в системе»; после сверки по этому ЗХ создана новая заявка.
- **When** открывает результат, затем переоткрывает его после создания заявки.
- **Then** в строке видны договоры и заявки найденного ЗХ (включая открепление),
  хотя он в другом статусе и, возможно, с другой СК; новая заявка появляется при
  следующем открытии; при этом категории и свод сверки не пересчитываются.

### SVERKA-E2E-15. Дополнение: Excel «Расхождения» и отсутствие колонок в «Запрос в СК»
- **Given** готовая сверка с заявками; экран открыт, данные live-колонок
  актуальны.
- **When** выгружает Excel.
- **Then** на листе «Расхождения» те же три колонки; номера договоров и заявок —
  рабочие гиперссылки; все заявки выводятся через перенос строки (не только 3);
  данные совпадают с экраном на момент выгрузки; на листе «Запрос в СК» этих
  колонок нет.

### SVERKA-E2E-16. HR не имеет доступа к разделу
- **Given** аутентифицирован пользователь клиента (HR).
- **When** открывает навигацию, затем прямую ссылку на раздел и запрашивает
  данные сверок.
- **Then** пункта раздела нет; прямой URL не показывает раздел и данные; запрос
  данных сверок отклоняется без раскрытия содержимого; сотрудник ГК при этом
  доступ имеет.

### SVERKA-E2E-17. Снимок результата и «Повторить»
- **Given** готовая сверка; после неё данные ЗХ в системе изменились.
- **When** пользователь переоткрывает сохранённый результат, затем нажимает
  «Повторить».
- **Then** сохранённый результат не изменился (категории, свод, подсветка и
  базовые колонки листа «Расхождения» — как на момент сверки; live-колонки
  дополнения и их данные в выгрузке — на момент открытия/выгрузки согласно
  INV-05); «Повторить» создаёт новую сверку по текущим данным, прежняя остаётся
  неизменной.

## 14. Приёмка и доказательства

- Приёмка — по пользовательским сценариям `scenarios[]` (ADR-KIT-091): каждый
  сценарий исполняется E2E на стенде, evidence — скриншот и ссылка на прогон
  (gate-scenario-coverage, fail-close).
- Сценарии опровержимы: каждый может упасть на реальном поведении, а не
  проверяет наличие кнопки.
- Инварианты с `status: active` на s06 обязаны иметь исполнимый `test_ref`;
  иначе инвариант остаётся `proposed`.
- Проверка Excel — по фактическому файлу (листы, строки, пустой «Ответ СК»,
  отсутствие внутренних категорий), а не по наличию кнопки.
- Проверка доступа HR — и через UI, и через серверную операцию.

## 15. Non-goals этого шага

Шаг s01 не пишет спеку, план, код, дизайн и не меняет существующее поведение.
Он не выбирает архитектуру и не декомпозирует фичу на юниты. Все открытые
вопросы остаются открытыми до груминга/s08; ответы в брифе не выдумываются.
