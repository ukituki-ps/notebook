## 4. Варианты реализации и рекомендация

### Вариант A — всё внутри notebook: локальные сущности + фикстуры

Домен сверки, справочные сущности и данные для сверки живут в репозитории
(seed-файлы/встроенные фикстуры), матчинг и UI работают на них.

- **Плюсы:** самодостаточность, детерминированные E2E, нет внешних согласований,
  можно поставлять по частям, все 17 сценариев проверяемы на `test2`.
- **Минусы:** доступ к фикстурам расползается по матчингу/результату/экспорту;
  замена на реальные источники станет переписыванием; высокий риск, что модель
  данных не совпадёт с системой (OQ-08/09/10).

### Вариант B — внешние интеграции (заглушки/адаптеры)

Справочник (ГК, СК, ЮЛ, договоры ЮЛ↔СК, ЗХ, договоры/заявки ЗХ) и адреса карточек
подключаются через адаптеры; на эту поставку — заглушка.

- **Плюсы:** явная граница, замена источника без переписывания домена, честное
  соответствие `out_of_scope` §8.2 (фича потребляет, но не создаёт справочники).
- **Минусы:** контракт порта проектируется до ответа OQ-10 и может оказаться
  неверным; больше подготовительной работы; стенду всё равно нужны
  детерминированные данные.

### Рекомендация: **B по границе, A по поставке**

Домен сверки обращается к справочнику через **узкий read-only порт** (выборки
«ГК», «СК по ГК», «договоры ГК↔СК», «ЗХ по договору/ФИО+ДР», «договоры ЗХ»,
«заявки ЗХ», «URL карточки договора/заявки»). На эту поставку порт реализуется
**серверным fixture-адаптером** (данные в репозитории, читаются приложением, не
мокаются в тестах). CRUD/миграции справочников не делаются.

Обоснование:

1. Источников нет и OQ-10 не закрыт; полноценная интеграция неверифицируема и
   выходит за объём трёх постановок.
2. Чистый вариант A без порта «зашивает» фикстуры в матчинг, результат и Excel —
   последующая замена источника станет переписыванием нескольких доменов.
3. Порт даёт planner/spec проверяемую границу и позволяет E2E на реальном HTTP
   стеке без моков юнита под тестом (`tools/check-no-self-mock.sh`).
4. Адреса карточек (OQ-02) входят в порт как конфигурируемые шаблоны, а не
   константы по коду.

Смежные рекомендации (не выбор юнитов):

- **Хранение сверок** — отдельный персистентный слой домена сверки (записи
  сверки + строки снимка + исходные файлы) на каталоге данных с volume; notes не
  переводить на него. Это единственный вариант, совместимый с текущим стендом
  (нет БД) и с INV-04/08/11.
- **Обработка** — фоновая goroutine в процессе + статус в хранилище + polling
  эндпоинт; зафиксировать single-instance и восстановление зависших статусов.
- **xlsx** — одна библиотека на чтение и запись (стили, автофильтр, freeze,
  гиперссылки) либо явный отказ от части форматирования; это решение OD-3 и оно
  определяет выполнимость FR-04 базы и FR-02 дополнения 3.
